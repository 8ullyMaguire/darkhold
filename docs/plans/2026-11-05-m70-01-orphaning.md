# M70-01 — the orphaning cascade: implementation plan

Status: corrected. **The first revision of this file was aimed at the wrong table** — corrected below.

## Correction: orphaning is about `works`, not `library_items`

The first revision planned a `library_items` rebuild. That table is the *reader's* imported library; it is their
personal data and should be deleted with the account, which is what the cascade already does correctly. The rows
that must survive orphaning are **authored works**:

    migrations/sqlite/0003_works.sql:41
      owner_pseud_id  TEXT  NOT NULL REFERENCES pseuds (id) ON DELETE CASCADE

    migrations/sqlite/0001_identity.sql:74
      account_id      TEXT  NOT NULL REFERENCES accounts (id) ON DELETE CASCADE

So the chain is `accounts → pseuds → works`, every link `NOT NULL … ON DELETE CASCADE`. Deleting an account takes
the pseuds, and the pseuds take the works. Ownership is per-pseud by design (ADR 0003), which is also why the frozen
label must come from the **pseud**, not the account — the domain rule already says so.

## The constraint the skill imposes

`db-migration-integrity` → `references/erasure-and-audit-rows.md`, first rule: **rekey in place; do not widen the
column to NULL.** Widening costs `DROP NOT NULL` on Postgres *plus a full table rebuild on SQLite*; the reference
says a rebuild is only for a constraint that genuinely must change, and flags the `_new` helper name as a trap for
gates that scan migration text.

That leaves one shape, and it is the one ADR 0003's model supports:

**Rekey the work to a detached pseud.** Orphaning creates a pseud row that belongs to no person and assigns the work
to it:

    pseuds: handle = 'orphaned', display_name = '<last pseud> (orphaned)',
            account_id = <detached-holdings account>, bio = NULL, discoverability = 'listed'

then `UPDATE works SET owner_pseud_id = <that pseud> WHERE id = ?`.

The work keeps its row, chapters, comments, collections and kudos; the author line reads `hollowgast (orphaned)`;
and the point of the shape is that the **real** pseud is then free to be deleted with its account, because nothing
references it any more. The largest content table is untouched.

## The one open decision — and why it is not settled here

`pseuds.account_id` is `NOT NULL REFERENCES accounts (id) ON DELETE CASCADE`, so a detached pseud still needs an
owner account row. Two ways to give it one, and they are not equivalent:

1. **A reserved system account** (`id = 'orphan-holdings'`, no credentials, no session, refused at login by an
   explicit check). One row created by the migration, never selected by any auth path. Cheap — but it is a
   person-shaped row that exists to be an owner, and every future `pseuds → accounts` join must know it is not a
   person.
2. **A nullable owner column on `pseuds`, with a CHECK that a pseud is either owned or detached.** More honest in
   the model — "belongs to nobody" is representable — but it costs the Postgres `DROP NOT NULL` plus the SQLite
   rebuild of `pseuds`, i.e. exactly what the skill says to avoid when a value change would do.

This deserves a recorded decision (ADR), because option 1 is a permanent *permission* question ("which account rows
are not people?") and option 2 is a permanent *schema* question. Do not pick one at the end of a session; the value
of the rekey shape is that it buys time to decide this properly.

## Steps once the decision is recorded

1. **ADR** `docs/adr/0004-orphaned-works-and-detached-ownership.md` — rejected alternative, erasure consequence,
   and the rule that a detached owner is never authenticated.
2. **Migration 0158** creates the holdings account (option 1) or the nullable column (option 2). **No `works` change
   either way.**
3. **`crates/db/src/orphan.rs`**: `orphan_work(db, work_id) -> Result<FrozenLabel, Refusal>`, one transaction: read
   the current pseud's display name, create the detached pseud, rekey the work, return
   `darkhold_domain::orphan::freeze(...)`. `Refusal::AlreadyAnOrphan` when the work's pseud is already detached.
4. **Account deletion** calls `orphan_works_of(account_id)` before `DELETE FROM accounts`, so the cascade finds no
   works to take. This is where the domain rule and the cascade meet.
5. **Erasure classification**: `works` moves from "cascade deletes it" to "erasure keeps it, rekeyed to a detached
   owner". The scaffolding test asserts the work survives, its title is still searchable, the author line ends in
   ` (orphaned)`, and the original pseud id appears in no row.
6. **Tests, both engines**: two works from one account; delete the account; both survive with frozen labels; search
   finds them by title; orphaning twice returns `AlreadyAnOrphan`; a *deleted* work is still deleted (orphaning is
   not a way to make deletion silently fail).

## Why the honest next action is an ADR

The choice between a system account and a nullable owner is not reversible the way a code change is: one puts a
fake person in the users table, the other rebuilds the identity table every request reads. Both are defensible;
they fail differently. That is what an ADR is for.

## Superseded first draft, kept for the record

It planned a `library_items` rebuild on the theory that `library_items` holds works. It does not: it holds a
reader's imported copies, whose deletion is correct. Three findings in that draft were about `library_items`
specifically and are **not** relevant to the corrected plan: its six canonical-date triggers, its five indexes, and
the `UNIQUE (account_id, source_key, source_work_key)` / NULL interaction. They are left out deliberately rather
than carried forward, because a plan that mentions work it does not do invites its re-execution.
