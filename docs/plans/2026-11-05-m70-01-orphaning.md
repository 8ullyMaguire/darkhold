# M70-01 — the orphaning cascade: implementation plan

Status: planned, not started. The rule is already shipped (`crates/domain/src/orphan.rs`, `df0f2840`); this file
covers the half that touches the schema.

## What is in the way

    migrations/sqlite/0009_library.sql:26
      account_id  TEXT  NOT NULL REFERENCES accounts (id) ON DELETE CASCADE

Deleting an account deletes every work with it. Orphaning wants the opposite: the row survives, the owner link
goes, the author line freezes. That needs the column nullable, the FK action changed, and a label column.

## Three discoveries that change the shape of the change

Recorded here because each one would otherwise be found the hard way, in production.

**1. `library_items` carries six CHECK triggers and six indexes.** Dumping the live schema shows
`library_items_canonical_{source_updated_at,last_synced_at,created_at}_{insert,update}` plus
`library_items_account`, `library_items_work`, `idx_library_items_source_likes`,
`idx_library_items_title_author_norm`, `idx_library_items_source_updated_at`. A SQLite table rebuild (the only
way to drop `NOT NULL`, since `ALTER TABLE` cannot) means recreating **all twelve**, in the same migration. Missing
one does not fail loudly — it silently stops validating dates or drops an index the planner was using.

**2. `UNIQUE (account_id, source_key, source_work_key)` changes meaning when `account_id` becomes nullable.**
SQL treats NULLs as distinct, so two orphaned copies of the same source work would both be allowed, and an
importer re-running after an orphaning would create a duplicate instead of finding the existing row. The
replacement constraint has to be explicit about it — either

    UNIQUE (coalesce(account_id, ''), source_key, source_work_key)

or a separate partial unique index over the orphaned rows. Pick one and write it down in the migration, because
whichever is chosen, the other is what the next reader will assume.

**3. Erasure's column list is not the only place that assumes the cascade.** `crates/db/src/erasure.rs` documents
that `DELETE FROM accounts` reaches every FK-linked table; `library_items` was one of them. After this change the
table is *reached and deliberately kept*, which is a new category: the scaffolding test must assert the work
survives **and** that the label froze **and** that the account id is gone, not merely that no row was orphaned
into the FK graph.

## The change, in order

### Step 1 — PostgreSQL (easy):

    ALTER TABLE library_items ALTER COLUMN account_id DROP NOT NULL;
    ALTER TABLE library_items DROP CONSTRAINT library_items_account_id_fkey;
    ALTER TABLE library_items ADD CONSTRAINT library_items_account_id_fkey
        FOREIGN KEY (account_id) REFERENCES accounts (id) ON DELETE SET NULL;
    ALTER TABLE library_items ADD COLUMN orphan_label TEXT;
    ALTER TABLE library_items ADD CONSTRAINT library_items_owner_or_label
        CHECK ((account_id IS NULL) = (orphan_label IS NOT NULL));

Verify: `SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'library_items'::regclass;`
expects `ON DELETE SET NULL` and the CHECK; `\d library_items` shows `account_id | text |` with no `not null`.

### Step 2 — SQLite (rebuild):

`PRAGMA foreign_keys=OFF;` → `CREATE TABLE library_items_new (…same columns, account_id without NOT NULL,
orphan_label TEXT, CHECK ((account_id IS NULL) = (orphan_label IS NOT NULL)), UNIQUE (coalesce(account_id, ''),
source_key, source_work_key))` → `INSERT INTO library_items_new SELECT …, NULL FROM library_items` →
`DROP TABLE library_items` → `ALTER TABLE library_items_new RENAME TO library_items` → recreate all six indexes
and all six triggers verbatim from `0009`/`0131` → `PRAGMA foreign_keys=ON;`.

Verification is a query, not a reading: `SELECT count(*) FROM sqlite_master WHERE tbl_name='library_items' AND
type='trigger';` must be **6**, and `SELECT count(*) … type='index'` must be **5** (the UNIQUE constraint's own
index is implicit) plus the partial one.

### Step 3 — the store:

    pub async fn orphan_works(db: &Database, account_id: &str) -> Result<u64, DbError>

One transaction: read the account's works with their pseud display names, `UPDATE library_items SET
orphan_label = <frozen>, account_id = NULL WHERE account_id = $1`, commit. Returns the count. Idempotent by
construction — a second call finds nothing with that account id and returns 0.

### Step 4 — the deletion path:

`erase_account` calls `orphan_works` **inside the same transaction** that deletes the account row, before the
delete. A partial state where the account went but the works still point at it cannot exist: the FK would be
violated, and SQLite reports it as a constraint failure only if `foreign_keys` is on — the test must set it.

### Step 5 — erasure classification:

Add an entry to `FK_FREE_ACCOUNT_COLUMNS`? **No** — the column is still in the FK graph. Instead extend the
scaffolding test's treatment vocabulary with a fourth kind, `Kept`, and assert: the row count for the account's
works is unchanged after erasure, every surviving row has `account_id IS NULL` and a non-NULL `orphan_label`, and
the label equals the frozen pseud captured before deletion.

### Step 6 — tests, both engines:

1. An account with two works is deleted; both works survive; labels are `<pseud> (orphaned)`; `account_id` is NULL.
2. Orphaning twice is a no-op returning 0 (there is no owner left to detach).
3. Search still finds an orphaned work by title — survival without discovery is the failure this row exists to
   avoid, and it is a separate assertion from survival.
4. A re-import of the same source work after orphaning does **not** create a duplicate (this is the UNIQUE/NULL
   discovery, and it needs its own test).

## Why not today

Steps 1–2 are a rebuild of a table that four subsystems read, with twelve schema objects to reproduce exactly, at
the end of a session whose verification budget was spent. The rule half shipped; the schema half gets a fresh
context and this file as its plan.
