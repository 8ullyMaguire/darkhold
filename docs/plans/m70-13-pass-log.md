## Pass 77 — the audience panel read a table nothing wrote (2026-11-09)

§41.2 defines warmth as a reader→author score with tiers, and every part of the rule exists: `warmth_delta` (ReadUnit 100,

* **The config knob is read, not decorative.** `CommunityConfig::warmth_thresholds` was a `serde_json::Value` that nothing parsed,

* **Best-effort.** A warmth failure is a `warn!`; a reader's kudos must not 500 because a derived panel could not update.
* **A reader cannot warm themselves.** The author acting on their own work is skipped, or the panel's `create` tier would count the

  warmth; a left-behind zero row makes `total` mean "ever interacted" while the panel is read as "currently warm".

## Pass 80 — quality signals: the filter dimension nothing could write (2026-11-10)

§32.1 calls `quality_signals` "typed, sourced, recomputable, 0..=1000"; §32.3 makes quality a *filter dimension*
(`min_quality:750`, `quality:editorial_review:750`) and the "Hidden gems" surface declares the table a data need. All of it compiled
and none of it could be fed: the only INSERT of a signal in the tree was in `milestone_22`'s own fixture (`source = 'test'`), and the
deployed table held **0 rows**. Every quality filter therefore answered "nothing" for the whole catalogue — which reads as "no such
work", not "nothing is scored".

Two doors, and the split is the decision:

* `POST /admin/works/{id}/quality-signals` — an operator records a judgement. `source` is `operator:<account>`, so a judgement is
  attributable and two operators cannot silently overwrite each other. A re-record by the same operator **replaces** their row:
  the composite is a weighted mean, so a duplicate doubles that signal's weight and outvotes everybody else's — measured, the
  value moves from 0.8 to 0.6 for two rows saying 800 and 400.
* `GET /works/{id}/quality` — public: the components plus the composite **using the filter's own formula**, so `0.8` here and
  `min_quality:0.8` in search describe one instance. Hiding the components while filtering on them is the worse half of that choice.

**Why the other kinds are not computed here.** `editorial_review`, `quorum_distinction` and `maturity` are judgements; a computed
`editorial_review` would be a review nobody performed. `completeness` and `reader_positivity` could be derived, but their mappings
are policy, not arithmetic — inventing them inside a route is how a scoring philosophy gets decided by accident. Named as the next
half.

**Two latent defects found by wiring the SQL.** `QualitySignal` declared `value: String` and `weight: f64` against BIGINT/INTEGER
columns — undecodable on *both* engines, so the reader was unreachable *and* unreadable; and the PostgreSQL arm compared the `UUID`
column to a text bind. Fixed (`value: i64`, `weight: i64`, `work_id::text = $1`), with the cast-the-column rule that also makes a
malformed id an empty list instead of a `500`.

Proof: red first (`GET /works/{id}/quality` was 404). Then, on both engines, the whole chain: door → 800 → composite `0.8` →
`min_quality:750` returns the scored work and not the unscored one; a correction replaces (0.4, one row); `vibes` → 422 naming
`kind`; `1001` → 422 naming `value`; a writer with no standing → 404. Mutants from /tmp: insert-without-replace (two rows, `0.6`) and
no-bounds-check (201 for `1001`).

Ratchet: 37 → 36 (`work_quality_signals` now has its caller).

## Pass 81 — `reader_positivity`: the signal the corpus can prove (2026-11-10)

Of the two kinds pass 80 named as derivable, `completeness` is **not** one: `completion:complete` is already a filter, so a derived
signal would be a second way to say the same thing with a number attached — a curve invented over a stored enum. Dropped with that
reason on record.

`reader_positivity` is arithmetic on something that exists: `darkhold_domain::positivity::classify` reads review text and returns a
class. The signal is `round(1000 * positive / visible)` over `positivity::visible_reviews` — the list the work page serves — and it is
**recomputed on every review write and deletion**, because an incremental average keeps the first reviewer's verdict winning forever.

Three states kept apart: no visible reviews → the computed row is **deleted** (absent, not `0`); visible non-positive reviews count in
the denominator (a visible critique is not praise); held reviews are not on the page and therefore not in the number.

**The placement defect this pass caught in itself.** The first version called the recompute *before* the positivity gate. `visible_reviews`
joins `review_classifications` with `(c.outcome IS NULL OR c.outcome = 'delivered')`, so a row with no classification yet counts as
visible — a **held** hostile review landed in the signal that exists to describe what readers see. Measured: the value moved to 500
when the held review should not have moved it at all. Moved after the gate, with the reason written at the call.

**Finding, recorded not fixed: the classifier delivers generic hostility.** `"This is awful and boring. I hate it."` classifies
**Positive** — it matches no `HOSTILE_MARKERS` phrase and falls through to `non-critical-engagement`. So the gate delivered it to the
author. The marker list is policy (adding `boring`/`awful` would also hold legitimate critique: "the villain was awful" is praise), so
this is a decision for the roadmap, not a list I extend in passing.

Proof: red first (no signal after a positive review). Then both engines: absent → `1000` (one positive) → hostile held and uncounted →
author opts into constructive, critique delivered, `500` → delete the positive, `0` (visible, not positive) → delete the critique,
absent again. Mutants: *every visible review counts as positive* (reddens the `500`) — this one **survived the first version of the
test**, which is why the visible-non-positive step exists; and *an empty page keeps the old row* (reddens the `None`).

Ratchet: 36 (unchanged; no orphans resolved or added).

## Pass 82 — the gate that delivered hostility as praise (2026-11-10)

Pass 81 recorded this as a finding rather than fixing it in passing. The classifier had a hole: text with **no marker at all** fell into
`non-critical-engagement`, which is `Positive`. So `"This is awful and boring. I hate it."` was delivered to the author as a review and
counted as praise by `reader_positivity`. Two consequences, one of them mine: the signal pass 81 shipped for a work could read `1.0`
because ten hostile reviews were classified positive.

The rule, and why it is shaped the way it is:

* **A verdict about the work is not hostility.** `HOSTILE_MARKERS` is about the person ("you are an idiot"); the file's own doc says so.
  Dislike of the work was the missing middle class, and `Negative` is the class the delivery matrix already holds.
* **Two distinct markers, not one.** "The villain was awful" is a reader praising the antagonist; "Awful ending, but I loved it" carries a
  positive marker anyway. One harsh adjective is colour, two without craft-specificity is a verdict nobody can act on.
* **Negation is filtered** in the twelve characters before each marker: "I don't hate it and it's not boring at all" is the opposite of
  what it contains.
* **Craft-specificity outranks the verdict.** "Awful and boring; the pacing drags and the dialogue is thin" is critique — actionable,
  and deliverable when the author opts in. Holding it would punish the reader who did the work of explaining.

Ordering is the whole design: hostile → all-caps → constructive → dislike → positive default.

**Two tests I had to fix because their mutants survived.** The negation test used one marker ("I don't hate it, honestly."), so the
threshold answered for the negation filter and deleting the filter changed nothing; the ordering test used one dislike marker, so
swapping the branches changed nothing. Both now carry the pair that makes the branch load-bearing — the failures were in my tests, not
in the rule.

**Also fixed, found by running the crate:** `cargo test -p darkhold-domain` was **red** before this pass — `taste_notifications` is
registered `default_on: false` with a written reason ("it writes to people who did not ask for it"), but it was missing from `OPT_IN`, so
the module-switch invariant demanded the opposite of what the registry said. Prose and checker disagreed; the checker's list was the
half that was missing.

Proof: red first (generic verdict → `Positive`). Both engines: the domain crate 1145 passed, `m16_07_review` 4/4 and
`m70_13_quality_positivity` 1/1 (which now also holds a *generic dislike* and shows the signal staying at 1000). Mutants, each red on
its intended assertion: threshold 1 instead of 2 (one harsh adjective), negation filter disabled (a negated pair), dislike branch moved
above constructive (actionable critique).

**Consequence for history, not fixed here:** classifications already stored keep their verdicts — a re-classification pass is a data
migration with its own reversible rule, and pretending the fix rewrote yesterday's rows would be a claim the database cannot support.

## Pass 83 — `ReadUnit`, the last of §41.2's four acts (2026-11-10)

## Pass 84 — `gate.sh dialects` was red on 14 sites; 12 were real (2026-11-10)

Found by running the gate rather than by planning a pass: `gate.sh dialects` failed on **14 sites in 9 files** — `tag_scripts`,
`content_policy`, `experiment_decisions`, `trope_clusters`, `experiment_snapshots`, `experiments`, `gravity_prefs`, `shelf_follows`,
`source_engagement`. The whole 0172–0178 migration family is another session's work, and every one of those tables types its timestamps
`TIMESTAMPTZ` while the code binds `now_rfc3339()`, a `String`.

**Reproduced against the server, not argued:**

    PREPARE bad(text) AS INSERT INTO probe_ts (id, created_at) VALUES (gen_random_uuid(), $1);
    ERROR: column "created_at" is of type timestamp with time zone but expression is of type text

and the fixed shape — `VALUES (gen_random_uuid(), $1::timestamptz)` — inserts. That is the whole class: a bind that SQLite accepts
and PostgreSQL refuses, invisible while every suite runs on SQLite.

**12 real defects fixed** by casting the placeholder (`$n::timestamptz`, `$n::uuid`) or the column in the SELECT (`::bigint` for INT4
columns decoded into `i64`, `to_char(... AT TIME ZONE 'UTC', ...)` where a TIMESTAMPTZ was read into a `String`).

**2 were the checker's fault, and fixing the checker was the fix.** The file's own docstring says a gate that reports correct code
teaches the reader to ignore it — and both false positives were of exactly that kind:

* `timestamptz_cast_sites` treated a **qualified** column (`s.created_at`, a TIMESTAMPTZ) as matching every table that has a TEXT
  `created_at`, so a correct cast was reported in `accounts` and `pseuds` — columns the statement never mentions. The alias prefix was
  optional inside a pattern that threw away what it captured. Now the qualifier is resolved through `alias_tables()`; an unqualified
  comparison still reports, because that is a possibility rather than a fact.
* `int4_sites` cut the SELECT list at the first literal `FROM`, so a correlated subquery's own `FROM` endeth the list early and its
  `ORDER BY n.position` became a "projection". Now the cut is at the first depth-0 `FROM`, subquery bodies are replaced with `(sub)`
  before projections are matched (COUNT is INT8), and function-call parentheses are kept — stripping `CAST(w.severity AS BIGINT)` down to
  `CAST(sub)` had turned a correct widening cast into a report.

Three self-test cases added for these shapes (one positive: an unqualified TEXT comparison must still report), 37 passing; the tree run
is `OK: no text bound to a typed column (389 tables)`.

**Why the suites did not catch it:** the gate reports 86 files claiming dual-backend coverage and 385 that make no such claim. These
features' tests are in the latter set — the same blind spot this ratchet keeps finding, one level up.

## Pass 85 — fourteen suites learned to run on PostgreSQL (2026-11-10)

`gate.sh dialects` also fails on `check-pg-arm-uses-sqlite-pool.py`: test helpers that reach `sqlite_pool()` with no backend arm make
their **whole file** SQLite-only. The list was longer than the gate's 40-line tail showed — 43 sites at the start, 18 now.

| helper | shape |
|---|---|

**Three fixture faults surfaced only on the deployed engine**, and each is the same blind spot one level down:
